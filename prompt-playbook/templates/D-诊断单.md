# D 型 · 诊断单

> **用途**：现象出现、需要定位根因。对应系统化调试四阶段。

## 模板（复制这一块）

```
【诊断】
现象：<用户可见的症状>
已知：<服务在跑 / 日志无 ERROR / 何时开始>
已排除：<试过什么，不管用>
请按序排查：
  (1) 异常是否被静默吞掉（except 里 pass / 日志无输出）
  (2) 类型问题（如 np.int64 不能绑 sqlite）
  (3) 环境变量不继承（systemd / 子进程）
  (4) 缓存与新数据错位（换索引没重启）
要求：结论必须指到 <文件:行>；每步先给"怎么验证"再给结论。
```

## 规范要点

- **"已排除"很重要** —— 避免 AI 重复你走过的死路。
- **排查顺序是踩过的坑的顺序**，可复用。上面四步是实战总结的顺序。
- **硬要求：结论必须指到具体一行**。指不到行 = 前提未验证。
- 先复现，不能稳定复现就不许改代码。

## 静默失败专项提示

"服务在跑、日志正常、但没反应"这类**完全静默**的故障，最可能的四处就是上面 (1)–(4)。
按序查，不要跳。经验：静默失效往往要 4 轮才定位，写成模板后可压到 1 轮。

## 常见误判

| 误判 | 纠正 |
|---|---|
| 直接改代码试错 | 先复现 + 打点，再改 |
| 靠打印猜哪里错 | 结论要指到行 |
| 只修表象 | 找到根因，问"同类路径还有没有" |
