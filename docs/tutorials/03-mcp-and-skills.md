# 03 · MCP 和 Skill 是什么

这两个词大概是新手最容易被劝退的地方。其实它们的区别用一句话就能说清楚，剩下的都是细节。

## 一句话区分

> **MCP 是「手」，负责够到外面；Skill 是「技能书」，负责教你怎么做。**

- **MCP（Model Context Protocol，模型上下文协议）** 解决的是「**能不能拿到**」——能不能查数据库、能不能读飞书、能不能开浏览器。
- **Skill（技能）** 解决的是「**拿到之后该怎么处理**」——按什么顺序做、什么该检查、输出成什么格式。

这个「手 / 技能书」的比喻不是我编的，中文圈那篇讲 Agent、MCP、上下文、Skill 区别的笔记就是这么类比的，我觉得比任何官方定义都好懂，直接拿来用了。

## 摆个表，把差别钉死

| | MCP | Skill |
|---|---|---|
| 它是什么 | 一个连外部系统的协议 | 一堆写在 Markdown 里的说明书 |
| 需要跑服务吗 | 需要，得有进程、要鉴权、要联网 | 不需要，就是几个文件 |
| 内容会不会变 | 会，数据库每分钟都在变 | 基本不变，除非有人去改它 |
| 占多少上下文 | 工具描述按需加载 | 平时只占一个名字和一句描述 |
| 能不能搬走 | 绑在那个系统上 | 一个文件夹，复制到哪儿都能用 |
| 典型用途 | 查订单、发消息、调 API | 按规范写周报、跑检查清单、统一输出格式 |

这张表参考了 Web Pulse 和 Red Hat 两篇的框架，它俩其实说的是同一件事，只是切入点不同。

## 为什么两个都要有

新手最容易犯的错，是把它当成二选一。真实情况是：**一个像样的 agent，两边都用。**

举个本仓库最常见的场景。「帮我根据飞书里的需求文档，改一下登录页」——

- 读飞书文档 → 靠 **MCP**（够到外部数据）
- 改代码前先读项目上下文、改完要跑验证、最后要写进错误台账 → 靠 **Skill**（固定的做事流程）

一个负责进货，一个负责炒菜的流程。缺了哪个，这顿饭都做不成。

## 那两个新词，顺带解释一下

**上下文工程（Context Engineering）。** 第 02 章提过，这里补一句：它的意思是在正确的时间，把正确的信息喂给模型。MCP 和 Skill 其实都是服务于它的两个手段——一个喂「外部数据」，一个喂「领域方法」。有篇文章的角度挺有意思，说整个 AI 领域的重心正在从「软件工程」滑向「上下文工程」，2024 年火起来的是 MCP，2025 年接棒的是 Skill，2026 年又冒出来 MCP Apps。这条演化线你不用背，知道「重心在往上下文走」就够了。

**渐进式披露（Progressive Disclosure）。** 这是 Skill 一个很聪明的设计。一个 skill 平时在上下文里只占一个名字加一句描述，大概几十个 token；只有当你做的事真的匹配上它了，agent 才会去读它的正文；正文里再引用更细的文档，用到才读。

好处很实际：**你装几十个 skill，不用的时候几乎不占地方。** 这也是为什么 Skill 特别适合承载「那份你一年才用两次、但用的时候一步都不能错」的流程。

## MCP 到底怎么工作的

你不需要会写 MCP 服务器，但值得知道它内部在转什么。

MCP 是 Anthropic 在 2024 年 11 月提出并开源的，后来交给了 Linux 基金会下面的 Agentic AI Foundation 托管，现在 OpenAI、Google、微软这些都在接。有人管它叫「Agent 时代的 USB-C」——一个通用插口，插上就能用，不用每接一个服务就写一套定制代码。

工作流程简化一下是这样：

1. 你配好一个 MCP 服务器（比如飞书），agent 启动时去「问」它：你有哪些工具？
2. 服务器把工具清单和说明报回来
3. agent 把这些说明放进上下文，模型就知道「原来我能查飞书」
4. 用户提需求，模型判断要调哪个工具，生成一段结构化的 JSON
5. MCP 服务器负责真正的 API 调用、鉴权、格式化
6. 结果再回到模型手里

注意第 5 步：**模型自始至终没有直接碰那个 API**，它只是生成了一段 JSON，剩下的是 MCP 在干。这就是为什么 MCP 能让「让 AI 访问你的系统」这件事变得可控——权限、鉴权都收在 MCP 这一层。

## 那你到底该用哪个

一个很好用的判断方法，来自 Web Pulse 那篇：**问自己，我的 agent 缺的到底是「够不到」，还是「没章法」。**

- 它老是做不成，是因为**够不到**它需要的那个系统 → 上 MCP
- 它什么都能碰到，但**每次做的结果都不一样**，没有稳定套路 → 写 Skill

这两个问题的解药完全不同。搞混了，你就会花一个礼拜去解决错误的那一半。

## 本仓库的两个 Skill

说了半天理论，看看实物。这个仓库里就两个 skill，正好是新手和进阶的两端：

- **`my-first-agent`** —— 极简版，零依赖，不需要任何 MCP。教新手的就一件事：一个三步循环。
- **`dev-automation-mcp`** —— 完整版，建议配 5 个 MCP。七步流程加五轮审核，是前者严格意义上的超集。

它们的文件结构长这样，你装任何第三方 skill 看到的也是同一套：

```
my-first-agent/
├── SKILL.md        # 正文，唯一的必需文件（开头是一小段元信息）
├── scripts/        # 可选，能直接跑的脚本
├── references/     # 可选，展开的详细文档，按需加载
└── agents/         # 可选，给某些工具看的展示信息
```

有个细节你可能会好奇：为什么每个 skill 都非得叫 `SKILL.md`？因为这是 Agent Skills 的开放标准，Anthropic 带头发起，现在 75 个以上的 agent 都认这套格式。**写一次，哪儿都能用**——这是它最大的价值，也是这个仓库敢把 skill 单独拎出来当卖点的原因。

## 这一章你要带走的一句话

> MCP 负责「够不够得到」，Skill 负责「做得好不好」。不是二选一，是分工。

---

**动手：** 打开本仓库的 `skills/my-first-agent/SKILL.md`，只读开头那一小段（`---` 包起来的部分）。你会看到它只有名字、一句描述、许可证这么几项。这就是一个 skill 在没被用到时，占的全部地方。
