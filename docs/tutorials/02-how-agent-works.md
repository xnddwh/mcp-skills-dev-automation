# 02 · Agent 是怎么工作的

这一章是全套教程里最值得你花时间的一章。看懂了它，后面所有东西——MCP、Skill、记忆、审核——你都能自己推出个大概。

## 先说大脑：LLM 只会「接话」

大语言模型（LLM）本质上做的事特别朴素：**看前面所有的文字，猜下一个字最可能是什么**，猜完再猜下一个，一直到停。

就这样？就这样。它没有记忆、没有计划、不会执行——它只是一台极其擅长接话的机器。

那它怎么能当 Agent 用？因为有两个东西改变了局面。

## 转折点：让它「调用工具」

第一个改变是**工具调用**（tool calling，有的地方叫 function calling）。

做法是这样的：你在发给模型的信息里，附带一份工具清单——每个工具有名字、有参数、有一句说明是干什么的。模型看到这些之后，它除了能回文字，还能回一种特殊的东西：「我要调用 `read_file`，参数是 `path=main.py`」。

注意这里的关键：**模型自己不执行任何东西**。它只是「申请」要调用某个工具。真正动手的是你写的程序——它读到这个申请，去跑对应函数，把结果再塞回给模型。

所以链条是这样的：

```
你写程序：给模型一堆工具 + 一个任务
模型：我想调用 search，关键词是「Python 版本管理」
你的程序：执行 search("Python 版本管理")，拿到结果
你的程序：把结果塞回给模型
模型：现在我知道答案了，回复用户……
```

第二个改变是**循环**。既然模型能看到工具的结果，那就别只做一轮——让它看了结果之后再决定下一步。这一循环，Agent 就诞生了。

## 循环长什么样

这套循环有个名字，叫 **ReAct**（Reason + Act，想和做）。名字不重要，形状重要：

```
┌─────────────────────────────────────────────┐
│                                             │
│   ① 想    模型读当前所有信息，决定下一步     │
│            ↕                                │
│   ② 做    调用一个工具，真的执行             │
│            ↕                                │
│   ③ 看    把工具结果放回上下文               │
│            ↕                                │
│   重复 ①②③，直到模型说「我做完了」          │
│                                             │
└─────────────────────────────────────────────┘
```

写出来一共就这么几行（Python 伪代码，看懂就行）：

```python
state = {"messages": [给模型的任务], "steps": 0}

while state["steps"] < 15:                  # ← 这个上限至关重要
    reply = 模型(state["messages"])          # ① 想
    if reply.想调用工具:
        result = 执行工具(reply.工具, reply.参数)   # ② 做
        state["messages"].append(result)     # ③ 看
        state["steps"] += 1
    else:
        return reply.内容                    # 模型觉得做完了，退出
```

如果你只记住一段代码，就记这段。里面那个 `state["steps"] < 15` 是保命的——没有它，模型可能会把同一个工具调二十遍，钱哗哗地流。Amanai Lab 那篇直接把它列进「最先崩掉的五件事」第一名。

> 🔬 **必须自己验证：** 上面是伪代码，看着对不等于跑得通。找一门你熟的语言敲出来，接一个最简单的工具（比如读一个文件）真跑一遍。跑通一次，你对「循环」的理解和只看代码完全不是一个档次。很多教程只给你看代码不给你跑，就是因为跑起来的问题它替你踩不了。

## 走一遍真实的循环

光看伪代码有点干。假设你让 agent「修一下登录按钮点了没反应的问题」，它内部大致是这样走的：

| 轮次 | 它想做什么 | 你看到的结果 |
|---|---|---|
| 1 | 得先看代码 | 调用 `read_file("login.js")`，拿到文件内容 |
| 2 | 再看历史踩坑记录 | 调用 `read_file("mistakes-ledger.md")` |
| 3 | 猜测是事件绑定的问题 | 直接回复一段分析，没调工具 |
| 4 | 想验证一下 | 调用 `search("addEventListener 未生效")` |
| 5 | 找到原因了，改吧 | 调用 `edit_file(...)` 改代码 |
| 6 | 改完得测 | 调用 `run("npm test")` |
| 7 | 测试过了，收工 | 回复「已修复，原因是 X，验证命令是 Y」 |

七轮。你会发现它一直在「看—想—做」之间来回，而**决定下一步干什么的始终是模型**，不是代码。这就是第 01 章说的「自主」。

## 上下文：它一次能记住多少

模型每次只能看到**有限长度的文字**，这个上限叫上下文窗口（context window）。所有东西都得挤进这里：你的任务、工具清单、之前每一轮的对话、工具返回的一大坨结果。

这就带来新手最容易忽视的一个坑：**工具返回的东西也占位置**。

你搜一个词，返回了 50 条结果全文，这几千字全塞进了上下文。跑个几轮，早期的关键信息就被挤出去了，模型开始「失忆」。学术界管这个叫 lost in the middle（夹在中间的信息最容易被忽略），实践中就叫上下文腐坏。

有个专业词叫**上下文工程**（context engineering），比提示词工程更进一层：不是光把话说好，而是**在正确的时候，把正确的信息放进上下文**。Red Hat 那篇把它定义得很清楚。你要做的具体动作通常是：

- 工具返回结果别照单全收，先砍到摘要再塞回去
- 闲聊历史太长了，压成一段总结
- 工具清单别一上来挂二十个，用不上的先收起来

## 为什么工具描述值得你反复改

模型是靠**工具的名字和那句说明**来决定什么时候该调用的。说明写糊了，它就会在该用的时候不调用，或者在不该用的时候乱调。

对比一下你就明白：

- 差：`search` —— 「搜索」
- 好：`search` —— 「在网上搜索近期新闻、论文或事实性信息。当问题需要训练数据之外的、实时的外部信息时使用。」

第二版多出来的那句「什么时候用」，才是真正起作用的部分。好几篇资料都强调这一点，Tech With Sanjay 甚至直接类比：**写系统提示词，像给新员工交代第一天的工作**——说清角色、目标、输出格式、不确定时怎么办、绝对别干什么。

## 两个能让循环更稳的细节

这两条不是必须的，但加上之后调试会轻松很多。

**让模型返回结构化结果。** 让它在做决定时回 JSON，而不是一段自由文字。结构化输出能明显减少解析错误，行为也更可预测——你不用再猜它这段话到底是在下指令还是在描述。

**工具报错要返回，别抛异常。** 工具失败时，把错误当成一条「观察结果」塞回上下文，而不是让整个程序崩掉。模型经常能自己换个思路重试，前提是它得**看见**那条错误。把它崩掉，等于剥夺了它自我修复的机会。

## 关键：它得知道什么时候该停

循环的危险全在这儿。如果模型不觉得任务完成，它会一直调工具，直到撞上 token 上限或者你的钱烧完。LearnAI 那篇给的办法很直接：**在系统提示里明确写「任务完成后，写出结果并结束回复」**。

停止条件通常有三层，都建议你配上：

1. 模型自己判断「做完了」
2. 步数上限（比如 15 轮）
3. 成本或时间上限

## 这一章你要带走的三句话

> 模型只会接话，是「工具调用 + 循环」把它变成了 Agent。
>
> 每一轮都要把工具结果塞回上下文，所以上下文是会满的——要学会压缩。
>
> 循环必须有停止条件，模型自己判断只是其中一层。

---

**动手：** 拿一张纸，把你昨天做过的一个小任务，拆成「想—做—看」的循环，写满五轮。写完你就会发现，很多事情你其实一直在用 ReAct 的思路做事，只是没给它起名字。
