# Lv3 · 流程与质量

五个练习，对应教程 06、07、08 章。这一级的主题从「能跑」变成「可靠」：踩坑、固化、评测、审计。做完你手里会有一套自己的评测集和一份从失败长出来的台账。

---

## Lv3-1 故意踩坑

**场景**：教程 06 列了十个坑，但坑这种东西看十遍不如踩一遍。

**目标**：在**无损失**的环境里真实踩中一个坑，并把它变成一条预防规则。

**步骤**

1. 复制一份目录当沙盒（和 Lv2-3 一样，绝不在原件上做）。
2. 挑一个坑。推荐坑 5（不给「不可逆操作要确认」的约束）或坑 3（不写停止条件）。
3. 故意**不写**那条约束，下任务，跑。
4. 观察并记录：它做了什么、你看到结果时的心情、损失是多少（在沙盒里应该是零）。
5. 立刻在副本里**补上约束重跑一次**，对比两次行为。

**查一查**

查你所用工具有没有**沙箱或权限限制**功能（能否限制目录、能否要求确认）。查完写进你的 `AGENT.md`——这是比口头约束更硬的一层。

**验收**

一条带 `Prevention rule` 和 `Verification next time` 的台账记录，外加一次「补上约束后行为改变」的对照证据。

**注意**

踩坑可以，越界不行。不碰真实的钱、真实的对外消息、真实的线上环境。沙盒里踩到的坑才叫练习，外面踩到的叫事故。

## Lv3-2 固化一个 skill

**场景**：你已经把某个任务重复做过三次以上了。每次都要重新交代，这就是该固化的信号。

**目标**：把一个重复任务写成 `SKILL.md`，并在新会话里用一句话触发成功。

**步骤**

1. 选任务。标准：你做过 ≥3 次、步骤说得清、验收能打勾。
2. 写 `SKILL.md`：frontmatter 两行（name、description）+ 步骤 + 验收。参考教程 04 的做法，**把「什么算做完」写进去**。
3. 装到你工具的 skills 目录，重启。
4. 开新会话，只用一句话触发，不加任何补充解释。
5. 验收结果。

**查一查**

去 Agent Skills 的官方规范（agentskills.io）核对两件事：必需字段是哪几个、description 的推荐写法。然后**回头检查你写的 description**——它决定这个 skill 什么时候被触发，写得含糊就永远不会被命中。这条在教程 03 的渐进式披露里讲过原理。

**验收**

新会话一句话触发成功，产出通过你写的验收标准。触发失败就改 description 重试——这个调试过程本身就是练习。

**注意**

第一个 skill 选**你自己重复过**的任务，别选「想象中别人会需要」的。你的台账里应该已经有现成素材了。

## Lv3-3 搭你的第一个评测集

**场景**：教程 07 那节「验证与评测」，现在把它落地。

**目标**：建一套 20 条可重复跑的场景，跑三遍，记录差异。

**步骤**

1. 选一个你已经有 agent 在做的任务（Lv2-3 的整理任务就很好）。
2. 写 20 条输入，按配比：**10 条正常、5 条边界、3 条对抗、2 条模糊**。边界如空文件夹、超长文件名；对抗如故意含糊的指令；模糊如没说清要什么。
3. 给每条写「什么算对」——一条写不出来，就说明这条场景你还没想清楚，先删掉。
4. 全部跑一遍，记录通过/失败。再跑第二遍、第三遍。
5. 对比三遍：**哪些条每次结果都不一样？** 把这些标出来——它们就是你系统里最不稳定的地方。

**查一查**

找一篇讲 agent 评估的资料（仓库教程 07 的来源清单里有现成的），核对两个定义：「轨迹评估」和「工具调用准确率」。然后回答一个问题：你这套 20 条，测的是**结果**还是**轨迹**？

**验收**

一张 20 × 3 的结果表，加上**至少 3 条从失败里长出来的新用例**——每次失败都该变成评测集的一条。

**注意**

最大的陷阱是只测 happy path。20 条里正常情况只能占一半，这是硬性要求，不是建议。

## Lv3-4 轨迹审计

**场景**：Lv2-3 你数过它调了几次工具。这次不只数，要找出**最浪费的那一步**并修掉它。

**目标**：完成一次前后对比的优化，用数字证明改进。

**步骤**

1. 跑一个任务，把**每一步**的输入、输出、工具调用全部记录下来（用工具自带的 trace，或直接让它汇报）。
2. 统计：总步数、工具调用次数、同一条命令重复了几次、哪些步骤的结果根本没被用到。
3. 找出最浪费的一步。常见嫌疑：同一文件读了两遍、工具描述太含糊导致选错、没有停止条件导致多绕几圈。
4. 只改**一处**（改工具描述，或补一条验收标准），重跑。
5. 对比：步数、耗时、结果质量。

**查一查**

查你所用工具的**观测/日志能力**官方文档：能不能导出完整轨迹、能不能按步骤看 token 消耗。查完记下来——这是你以后调试的入口，比改措辞有用得多。

**验收**

一张前后对比表（步数 / 耗时 / 结果），加一条你写进 `AGENT.md` 的改进规则。

**注意**

一次只改一处。同时改三个变量，变好了你不知道该谢谁，变坏了你不知道该怪谁。

## Lv3-5 升级到完整版

**场景**：三步循环你已经跑熟了，该看看「完整版」多出来的是什么。

**目标**：从 `my-first-agent` 切到 `dev-automation-mcp`，跑通一次真实的开发任务。

**步骤**

1. 装完整版 skill（安装方式见仓库 [`INSTALL.md`](../../INSTALL.md)）。
2. 把 `AGENT.md` 的内容并进完整版读的文件，错误台账沿用同一份——这两个衔接动作教程 08 讲过。
3. 挑一个**小的真实开发任务**（改一个小 bug、加一个小功能）。
4. 按七步流程走完，重点体会三步循环里没有的东西：**查证**、**验证**、**五轮审核**。
5. 复盘：多出来的哪几步真的拦住了问题？哪几步对这个任务是空转的？

**查一查**

打开本仓库的 [`skills/dev-automation-mcp/SKILL.md`](../../../skills/dev-automation-mcp/SKILL.md)，把它的八条硬规则和你这几个练习里自己总结出来的规矩**逐条对照**。你会发现大部分你已经在坑里撞过了——这就是这套练习的设计逻辑：先撞墙，再看墙上的图。

**验收**

一次完整的「读上下文 → 改 → 验证 → 审核 → 复盘」记录，外加一条你自己的结论：完整版里哪几步对你现在的工作是真的有用。

**注意**

别因为「完整版更全」就全程用。教程 08 的观点是深浅两档选一个，标准是你**真实需要**哪几步。这次练习的目的就是让你有依据地做这个选择。
