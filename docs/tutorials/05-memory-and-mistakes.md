# 05 · 记忆与错误台账

上一章你生成了 `AGENT.md` 和 `mistakes-ledger.md`。这一章讲清楚：这两个文件为什么存在，以及怎么写才真的有用——因为照着模板填一堆废话，等于没写。

## 为什么 agent 需要「记忆」

先破除一个幻想：**agent 本身什么都不会记得。**

每次你开一个新对话，对它来说都是全新的开始。上一轮它帮你解决了什么、你偏好什么写法、上次那个坑是怎么踩的，它统统不知道。上下文窗口是个「短期记忆」，聊完就散。

这就是为什么几乎所有资料都把「记忆」列进必做项。AI Discoveries 那篇说的话我前面引用过——没有记忆的 agent 只是一台昂贵的聊天机器人。它不是在夸张，是在描述一个很具体的失败：你花了两小时调教出一个好用的助手，关掉窗口，明天它又变回白纸。

解决办法不是让模型「记住」（你控制不了它内部），而是**把该记的东西落到文件里，每次开工前让它先读**。这叫外置记忆，或者叫项目记忆。简单，可靠，你能看见，也能改。

## 两个文件，分工明确

本仓库用两个文件承担这件事，它们管的东西不一样，别混：

| 文件 | 管什么 | 类比 |
|---|---|---|
| `AGENT.md`（完整版里叫 `CLAUDE.md`） | **长期不变的事实**：你是谁、项目目标、技术栈、常用命令、架构约束 | 员工手册 |
| `mistakes-ledger.md` | **踩过的坑**：什么时候、错在哪、根因、怎么防 | 事故档案 |

判断一个信息该进哪个文件，问一句就够了：**它是不是「一次教训」？** 是，进台账；不是（是稳定的事实或规则），进 `AGENT.md`。

## 错误台账：字段为什么这么设计

很多人第一次看到这个模板会觉得有点重：

```markdown
### YYYY-MM-DD - 标题

- Context:      当时在什么情境下
- Mistake:      具体错在哪
- Root cause:   为什么会错
- Detection signal: 下次怎么一眼看出又要错了
- Prevention rule:  下次该怎么做
- Verification next time: 怎么确认这次没再犯
```

六个字段，一个都不能省，因为每个字段在防一件特定的事：

- **Context** 防止你脱离场景照搬教训。别处的经验不一定适合这里。
- **Mistake** 只记「错了什么」不够，得具体到能被辨认。
- **Root cause** 是最容易被跳过、也最关键的一个。只记「现象」的话，下次换个表象你照样栽。
- **Detection signal** 是这份台账真正的杀手锏。它让你**在错误发生之前**就有警觉，而不是又踩完才想起来。
- **Prevention rule** 是你希望 agent 下次动手前能说出来的那句话。
- **Verification next time** 把「我记得」变成「我验证过」。

两个字段我特意用了英文名，因为完整版 `dev-automation-mcp` 用的就是这套字段，两个 skill 共用同一个台账文件，字段一旦不一致就没法互操作了。

## 一条烂记录 vs 一条好记录

这是这一章最实用的部分。对比着看：

**烂记录**

```markdown
### 2026-10-01 - CSS 有问题
- Context: 改样式
- Mistake: 改完没效果
- Root cause: 不知道
- Prevention rule: 小心点
```

这条记录你一个月后回来看，会完全不知道当时发生了什么。「小心点」不是规则，是许愿。

**好记录**

```markdown
### 2026-10-01 - 改完 CSS 浏览器没变化
- Context: 修改 header 的高度，保存后刷新页面无变化
- Mistake: 直接改完就断言"已修复"，实际用户看到的是旧样式
- Root cause: 浏览器缓存了旧 CSS；改动本身没问题
- Detection signal: 改样式后页面"完全没反应"，往往是缓存而非代码错
- Prevention rule: 改 CSS 后先硬刷新（Ctrl+Shift+R）再判断，必要时加版本号
- Verification next time: 改完先硬刷新确认变化，再跑一次构建确认产物更新
```

看出来了吗？差别不在字数，在于「下次真的能用」。好记录里那条 `Detection signal` 甚至能让你在**还没开始改的时候**就预判到问题。

我在 `first-tasks.md` 的任务 3 里故意让你去踩一个坑，就是为了让你亲手写出一条这种质量的记录。写不出来就说明你还没搞清根因，那就再挖一层。

## 怎么让它真的被读起来

写了不读，等于没写。让台账起作用，靠的是**规则**，不是自觉：

- 开始任务前，先读台账——这条写进了两个 skill 的硬规则里，agent 必须先读完才准动手
- 一旦出现返工、误判、漏测、配置错、来源错，**立刻追加一条**，别攒着
- 再遇到同类任务时，agent 要**明确说出**这次适用哪条预防规则，而不是默默跳过

最后这条是关键：`dev-automation-mcp` 的流程里有一步专门要求「显式写出本次适用的预防规则」。要它说出来，你才知道它到底有没有读到。

## 别让它变成垃圾场

记忆这事有个反方向的坑：**什么都往里塞**。AI Discoveries 那篇有句话我划了线——「不要什么都存，只存那些能改善未来任务的」。

两条实操建议：

- `AGENT.md` 只放**长期有效**的东西。临时调试用的路径、一次性的命令，别放，它们会稀释真正重要的信息。
- 台账要**定期归档**。一百条里可能有八十条早就没用了。本仓库路线图里列了一个 `memory-audit` 的待做 skill，就是干这个的：定期清掉过期的，让台账保持能被读完的长度。

一个塞满噪音的记忆文件，比没有记忆还糟——它让 agent 每次都读到一堆无关信息，还占上下文。

## 这一章你要带走的一句话

> 模型自己不会记住任何东西。记忆是你外置到文件里、并且强制它开工前先读的那部分。
