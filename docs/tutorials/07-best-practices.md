# 07 · 最佳实践清单

第 06 章讲的是「别做什么」，这一章讲「该怎么做」。我把它整理成一份可以直接贴在墙上的清单，每次动手新东西之前扫一眼。

清单的顺序不是随便排的——它大致按你「从零到有」的时间线走：先想清楚要做什么，再动手，再测，最后才谈上线。

## 动手之前

**先把目标写成人话。** 一句话能说清「什么算做完了」才开工。有资料提到，超过四成的项目失败源头是目标模糊。写不出这句，说明你自己还没想清楚。

**从最小的能用的版本开始。** 一个任务、一个模型、两三个工具、一层薄薄的记忆。复杂度随时可以加，清晰度加不回来。

**先自己想一遍流程。** 你打算让它怎么做这件事？如果连你说都说不利索，模型更理不顺。

## 设计的时候

**一个工具只干一件事。** 拆到原子级别。一个既查数据又发邮件的工具，出问题时你连它错在哪一半都不知道。

**工具说明写到「什么时候用」。** 这是最容易被省、也最值钱的一句话。名字要能自解释，参数要严格，说明里必须包含使用场景。

**显式写出停止条件。** 在提示里明说不止一遍：任务完成后要输出结果并结束。

**决定记忆存什么，而不是存多少。** 只存能改善未来任务的信息。这个判断标准要一直用。

**把规划跟执行分开想。** 就算你最后还是用一个 agent，思考的时候也该分开：这一层是「把大目标拆成小步骤」，那一层是「老老实实执行每一步」。想清楚了再决定要不要真的拆成两个。

## 防护

**权限从小到大。** 只读起步，确认可靠了再逐步放开写权限。别第一天就把生产数据库的写权限交出去。

**不可逆动作必须有人确认。** 发邮件、付款、删数据、改线上配置——没有任何例外。

**设硬上限。** 步数、超时、token 预算，三个都配上。一个能永远跑下去的 agent，也能永远花钱。

**工具报错要能被看见。** 工具失败时，把错误当成一条「观察结果」返回给模型，而不是直接抛异常把程序搞崩。模型经常能自己换个思路重试。

## 验证

**从第一版就加日志。** 每一轮的输入、输出、工具调用、工具结果都记下来。这不是为了排查故障才做的，是你理解 agent 行为的唯一途径。

**建一批可重复的测试场景。** 别用「我测过」这种话糊弄自己。正常、边界、空白、对抗，四类都要有。

**先固定一批题，再改东西。** 改了提示词或工具之后，用同一批场景重跑，你才知道是变好了还是变坏了。这就是为什么测试场景要能重复跑。

**看轨迹，不只看结尾。** 一个任务完成率是 90%，听起来不错；但如果剩下那 10% 是悄无声息地失败，那就很危险。

## 成本

**从第一天就记账。** 每个任务花多少 token，心里有个数。

**分层用模型。** 简单分类、检索交给便宜快的；复杂推理才用贵的。这一条能省下的钱比你想的多。

**砍上下文。** 老的对话历史压成摘要，工具返回的大段内容先砍到重点再塞回去。上下文又贵又有限，能省则省。

**结果能缓存的就缓存。** 同一个查询何必每次都重新跑一遍。

## 写提示词的时候

- 把它当新员工交代：角色、目标、输出格式、不确定怎么办、禁止做什么
- 要求结构化输出（比如让它返回 JSON），能大幅减少解析错误
- 说清「事实」和「推断」的区别——不确定的让它标出来，别让它编
- 引用要有出处，没有来源的结论要标「待确认」

## 验证与评测：别只看最终答案

清单里反复出现「要测试」，这里把它单独拎出来说，因为这是新手最容易低估的一块。

**只看结果会漏掉大问题。** 同一个正确答案，可能来自三次精准调用，也可能来自十二次乱试。从结果看都「做完了」，但后者的成本是前者的好几倍，中途还可能踩了你不希望它踩的东西。这叫**轨迹评估**——不只看它最后交了什么，还看它这一路怎么走的。

**评测集要从失败里长出来。** 别指望一开始就写出一套完美的测试题。实际做法是：先随手准备十几条能重复跑的场景，然后**每次 agent 出错，就把这次失败加进评测集**。攒几个月，这套东西就是你的质量保证——它记录的是这个 agent 踩过的每一个坑。

**四类输入都要有。** 一个全是「正常情况」的评测集什么都发现不了。大致比例：一半正常，四分之一边界（缺数据、超长输入），一成半对抗（故意刁难），一成模糊（需求本身说不清）。比例不用死记，记住「正常情况只能占一半」就够了。

🖐️ **必须亲手做：** 出题可以交给 AI，但「什么算失败」的判断标准只能你定。先拿手上的 agent 把同一个小任务跑十次，把每次的差异记下来——你会惊讶于同一条指令能走出多少条不同的路。这份差异清单，就是你评测集的第一批题目。

## 一张速查表

真到动手的时候，看这一张就够了：

| 阶段 | 一句话 |
|---|---|
| 开工前 | 目标写成一句能被验收的话 |
| 起步 | 一个任务、两三个工具，别多 |
| 工具 | 一件一 tool，说明要写「何时用」 |
| 循环 | 必须有步数上限和明确的结束条件 |
| 权限 | 从只读开始，不可逆的必须人工确认 |
| 日志 | 第一版就要，别等出事 |
| 测试 | 一批可重复的场景，包含刁钻输入 |
| 成本 | 设预算，分层用模型，砍上下文 |
| 记忆 | 只存有用的，定期清理 |
