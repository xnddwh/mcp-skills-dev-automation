# Skill 分类与搭配推荐

装 skill 最容易犯的错，是「看到一个装一个」。装到十几个之后你会发现两件事：一是它们开始互相抢触发词，二是你根本记不住哪个该在什么时候用。

这一章给一套分类方法，再给几套现成的搭配方案。目的很实际：**让你知道手里每个 skill 站在哪一层，以及哪几个该放一起用**。

## 一条主轴：它作用于哪一层

分类只用一个判据——**这个 skill 的「作用对象」是什么**。是过程、知识、材料，还是外部系统？

这个主轴的好处是它直接解释了「为什么不能乱叠」：**同一层的 skill 放两个，就会互相打架**；不同层的 skill，天然互补。

### 三步判类

拿到一个陌生的 skill，按顺序问三个问题，第一个「是」就是它的类别：

1. **它会改变外部系统的状态吗？**（要凭据、要跑 CLI、有不可逆后果）→ 是，**D 类 · 系统操作**
2. **它强绑定某个垂直领域吗？**（换成别的领域就没用了）→ 是，**B 类 · 领域专家**
3. **它是在把已有材料变形，还是在规定做事的方式？**
   - 变形材料（改写、归类、提炼）→ **C 类 · 产出加工**
   - 规定方式（跟领域无关）→ **A 类 · 协作规范**

一个 skill 一般只落一类。真跨界的（比如既像领域又像加工），按**它最主要的作用**判，然后在说明里备注另一重身份。

### 四类总览

| 类别 | 作用对象 | 一句话 | 适用场景 | 典型示例 |
|---|---|---|---|---|
| **A 协作规范** | 过程 | 规定 agent 怎么干活 | 跨领域、长期用、当底座 | `my-first-agent`、`dev-automation-mcp` |
| **B 领域专家** | 知识 | 携带某个领域的知识与判断标准 | 该领域的具体问题 | 数学解题、阅读精析这类 |
| **C 产出加工** | 材料 | 把已有材料变成更可用的形态 | 有草稿或素材之后 | `humanizer-zh`、`obsidian-vault-governance` |
| **D 系统操作** | 系统 | 直接读写外部系统 | 部署、运维、排障 | `byted-supabase`、静默故障排查这类 |

## 逐类说明

### A 类 · 协作规范

**它管什么。** 管**过程**，不管结果。它不告诉你「这道题怎么解」，只规定「动手前先读记忆、改完必须验证」。抽掉一切领域知识它依然成立——这正是判据。

**什么时候用。** 任何时候。它是底座，长期挂着。

**这一类最关键的守则是：只留一个。** 两个底座同时装，规则会撞车、触发词会互抢。同一套流程的「深浅两档」（比如 `my-first-agent` 和 `dev-automation-mcp`）是**同一个底座的两个版本**，不是两个 skill，选一个就行。

**典型示例：**

- `my-first-agent` —— 三步循环，零依赖。适合新项目、新领域的第一周。
- `dev-automation-mcp` —— 七步流程 + 五轮审核，建议配 MCP。适合碰真项目。

### B 类 · 领域专家

**它管什么。** 携带一个垂直领域的知识和判断标准。它的价值不在「会用工具」，而在**知道这个领域的正确答案长什么样**。

**什么时候用。** 你在这个领域有具体问题要解的时候。

**这一类是数量最多、也最容易过剩的**。因为领域知识强绑定主业，**主业一换，旧的就成了纯占位**。建议只挂当前主战场的那几个。

按「你给它什么输入」还能再分四小类：

| 细分 | 输入 | 输出 | 示例 |
|---|---|---|---|
| B1 总管型 | 一个模糊需求 | 调度与计划 | `kaoyan` |
| B2 调研型 | 一个决策问题 | 有证据约束的判断 | `kaoyan-navigator` |
| B3 解题型 | 一道题 / 一个概念 | 可追溯的推导 | `dxsm-math`、`kaoyan-11408` |
| B4 训练型 | 一批素材 | 反馈循环 + 越攒越厚的库 | `kaoyan-english-one-sentence-trainer`、`reading-analysis` |

B4 值得单独说：它和另外三种**质上不同**——它会**积累**。每用一次，它内部的案例库/错题模式就厚一层。所以 B4 类 skill 的价值随时间上升，值得长期挂着。

### C 类 · 产出加工

**它管什么。** 不生产新知识，只改变**材料的形态**：删 AI 味、归类、结构化、建索引。

**什么时候用。** 你已经有东西了，但它的形态不能直接交付或沉淀。

**这一类几乎无副作用，可以放心长挂。** 它唯一的风险是「太顺手」——把不该改的东西也一起改了（比如 humanizer 改风格时顺手动了事实）。

**典型示例：**

- `humanizer-zh` —— 改文字风格，保原意。
- `obsidian-vault-governance` —— 改知识库的结构：归类、去重、建双链。

> **一个易混点**：`obsidian-vault-governance` 看起来像 D 类（它会移动、删除文件），但它的主要作用是**材料形态的转换**，而且它自带「只读盘点 → 列清单 → 确认后才执行」的强约束，把副作用收得很紧。所以归 C。判定标准是**主要作用**，不是「有没有副作用」。

### D 类 · 系统操作

**它管什么。** 直接读写外部系统：数据库、服务器、部署环境。

**什么时候用。** 真的要动线上/远端的东西时。

**这一类必须从严。** 三条硬规矩：

1. **只装你真在用的。** 一个不碰的数据库 skill 挂在身上，只是多一个被误触发的机会。
2. **必须配人工确认。** 不可逆操作（停机、删数据）在动手前要复述影响并二次确认。
3. **先只读、后写入。** 任何变更前先跑查询确认现状，变更后再查一次确认生效。

**典型示例：**

- `byted-supabase` —— 操作火山引擎 Supabase（含高危的 workspace 暂停红线）。
- 静默故障排查类 —— 诊断运行中的服务。

## 搭配推荐方案

### 组合的基本逻辑

一次完整的作业，最多只需要四样东西，正好对应四层：

```
        ┌──────────────────────────────┐
        │  A 底座：怎么干               │  ← 长期固定，只留一个
        ├──────────────────────────────┤
        │  B 领域：干什么 + 怎么判对错   │  ← 跟当前主业走
        ├──────────────────────────────┤
        │  C 加工：产出成什么形态        │  ← 按需，可长挂
        ├──────────────────────────────┤
        │  D 执行：动什么（有副作用）    │  ← 从严，必须有人把关
        └──────────────────────────────┘
```

**不是每次都要四层。** 大部分任务只需要 A + B。C 是「有产出之后」才加，D 是「要动真东西」才加。

### 四条搭配原则

1. **底座只留一个** —— 同层叠加会抢触发词、规则互斥。深浅两档二选一。
2. **领域层跟着主业走** —— 别把不相干的领域都挂着，它们会稀释匹配准确度。
3. **加工层可以长挂** —— 成本低、副作用小，唯一要盯的是「别改到不该改的」。
4. **执行层从严** —— 装最少的、配确认的、先只读的。

### 四套现成搭配

**套餐 A · 应试闭环**（主线：学习 → 做题 → 沉淀）

> 组成：**A**（一个底座）+ **B1 总管** + **B3 解题** + **B4 训练** + **C 知识治理**

- 逻辑：总管负责「今天干什么」，分科解题/训练负责「具体怎么打」，知识治理负责「打过的别再忘」。
- 适用：有明确考试/学习主线的人。
- 注意：**只挂当前主战场的那一两科**，考完的科目及时撤下来。

**套餐 B · 内容生产**（主线：素材 → 成稿 → 交付）

> 组成：**B**（领域产出初稿）+ **C**（风格加工）→ 交付

- 逻辑：领域 skill 负责「说得对」，加工 skill 负责「读着像人写的」。两步顺序不能反——先保正确，再改风格。
- 适用：要往外发东西的时候。
- 注意：加工层**只改风格不改事实**，改完自己再核一遍关键数字。

**套餐 C · 工程开发**（主线：读上下文 → 改 → 验证 → 审核）

> 组成：**A**（开发向底座）+ **D**（需要的 MCP 能力，如搜索/浏览器/文档）

- 逻辑：底座提供流程（先读记忆、最小改动、跑验证、多轮审核），D 层提供「够到外部」的能力。
- 适用：碰真代码库时。
- 注意：MCP **能配就配、配不上就按降级规则走**，别为了凑齐工具卡住。

**套餐 D · 生产运维**（主线：查现状 → 变更 → 验证）

> 组成：**D**（系统操作）+ **D**（诊断/排障）

- 逻辑：一个负责「动」，一个负责「坏了怎么查」。两者都要强护栏。
- 适用：手上有真在跑的服务时。
- 注意：这是四套里唯一**默认应该加人工确认**的一套。装之前先问自己：这东西误触发了，最坏会怎样？

## 落到我自己的 skill

按上面三步判类，我当前已装的 skill 分布如下（同一 skill 在多处有副本的只列一次）：

| 类别 | 我的 skill | 备注 |
|---|---|---|
| **A 协作规范** | `my-first-agent`、`dev-automation-mcp` | ⚠️ 同一个底座的两档，**该二选一**，别同时挂 |
| **B1 总管** | `kaoyan` | 考研总入口 |
| **B2 调研** | `kaoyan-navigator` | 择校有据调研 |
| **B3 解题** | `dxsm-math`、`kaoyan-11408` | 数学、408 + 数一 |
| **B4 训练** | `kaoyan-english-one-sentence-trainer`、`reading-analysis` | 会越用越厚，值得长挂 |
| **C 产出加工** | `humanizer-zh`、`obsidian-vault-governance` | 可长挂 |
| **D 系统操作** | `byted-supabase`、`nonebot-silent-failure-triage` | 从严，配确认 |

**从这张表能直接看出两个问题：**

1. **A 层目前有两个**（`my-first-agent` + `dev-automation-mcp`）。按原则 1 应该只留一个——过渡期可以先都放着，但心里清楚它们是同一层。
2. **B 层偏重但方向一致**（全部围绕考研），这没问题，因为你主业就是它。等到主线切换时，**这一整层要成批替换**，不要把旧的一直挂着。

## 附录 · 该不该装一个 skill

装之前过四个问题，任何一个答不上来就别装：

1. **它属于哪一层？** 判不出类别，说明你还没看懂它，先别装。
2. **这一层已经有 skill 了吗？** 有，且功能重叠 → 只留一个。
3. **我最近一个月会用到它吗？** 不会 → 等要用再装。装 skill 是零成本，但**误触发不是**。
4. **它有副作用吗？** 有 → 它属于 D 层，先确认它的护栏够不够。
