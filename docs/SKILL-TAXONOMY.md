# Skill 分类与搭配推荐

装 skill 最容易犯的错是「看到一个装一个」。装到十几个之后你会发现两件事：它们开始互相抢触发词；你根本记不住哪个该在什么时候用。

这一章给一套分类方法，再给几套现成的搭配方案。

> **关于本文的链接**：文中每个 skill 都尽量给了来源链接，方便你直接去看原文和许可证。
> 少数几个查不到公开来源，我把它们指向文末的[来源说明](#来源说明)——**没有编造链接**。
> 判断一个 skill 能不能转载，看的是链接那一头的许可证。

## 一条主轴：它作用于哪一层

分类只用**一个**判据——这个 skill 的「作用对象」是什么。是过程、知识、材料，还是外部系统？

用一条主轴的好处，是它顺手解释了「为什么不能乱叠」：**同一层的 skill 放两个，就会互相打架**；不同层的，天然互补。

### 三步判类

拿到一个陌生的 skill，按顺序问三个问题，第一个「是」就是它的类别：

1. **它会改变外部系统的状态吗？**（要凭据、要跑 CLI、有不可逆后果）→ 是，**D 类 · 系统操作**
2. **它强绑定某个垂直领域吗？**（换个领域就没用了）→ 是，**B 类 · 领域专家**
3. **它是在把已有材料变形，还是在规定做事的方式？**
   - 变形材料（改写、归类、提炼）→ **C 类 · 产出加工**
   - 规定方式（跟领域无关）→ **A 类 · 协作规范**

多数 skill 只落一类。真跨界的，按**它最主要的作用**判，再在说明里备注另一重身份。

### 四类总览

| 类别 | 作用对象 | 一句话 | 适用场景 | 示例 |
|---|---|---|---|---|
| **A 协作规范** | 过程 | 规定 agent 怎么干活 | 跨领域、长期用、当底座 | [my-first-agent](../skills/my-first-agent/) · [dev-automation-mcp](../skills/dev-automation-mcp/) |
| **B 领域专家** | 知识 | 携带某领域的知识与判断标准 | 该领域的具体问题 | [kaoyan-11408](https://github.com/Kosthi/11408.skill)（408 与数一） |
| **C 产出加工** | 材料 | 把已有材料变成更好用的形态 | 有草稿或素材之后 | [humanizer-zh](https://github.com/op7418/Humanizer-zh) |
| **D 系统操作** | 系统 | 直接读写外部系统 | 部署、运维、排障 | [byted-supabase](https://www.volcengine.com/) |

## 逐类说明

### A 类 · 协作规范

**它管什么。** 管**过程**，不管结果。它不告诉你「这道题怎么解」，只规定「动手前先读记忆、改完必须验证」。把一切领域知识抽掉，它依然成立——这就是判据。

**什么时候用。** 任何时候。它是底座，长期挂着。

**这一类最要紧的守则是：只留一个。** 两个底座同时装，规则会撞车、触发词会互抢。同一套流程的「深浅两档」是**同一个底座的两个版本**，不是两个 skill，选一个就行。

**典型示例：**

- [my-first-agent](../skills/my-first-agent/) —— 三步循环，零依赖。适合新项目、新领域的第一周。
- [dev-automation-mcp](../skills/dev-automation-mcp/) —— 七步流程加五轮审核，建议配 MCP。适合碰真项目。

### B 类 · 领域专家

**它管什么。** 携带一个垂直领域的知识和判断标准。它的价值不在「会用工具」，而在**知道这个领域的正确答案长什么样**。

**什么时候用。** 你在这个领域有具体问题要解的时候。

**这一类数量最多，也最容易过剩。** 因为领域知识强绑定主业，**主业一换，旧的就只剩占位**。建议只挂当前主战场的那几个。

按「你给它什么输入」还能再分四小类：

| 细分 | 输入 | 输出 | 示例 |
|---|---|---|---|
| B1 总管型 | 一个模糊需求 | 调度与计划 | kaoyan（[来源未公开](#来源说明)） |
| B2 调研型 | 一个决策问题 | 有证据约束的判断 | [kaoyan-navigator](https://github.com/mcxiaoxiao/kaoyan-navigator-skill) |
| B3 解题型 | 一道题或一个概念 | 可追溯的推导 | [kaoyan-11408](https://github.com/Kosthi/11408.skill) · dxsm-math（[来源未公开](#来源说明)） |
| B4 训练型 | 一批素材 | 反馈循环，越攒越厚 | [kaoyan-english-one-sentence-trainer](https://github.com/singgou/kaoyan-english-one-sentence-trainer) · [reading-analysis](https://github.com/shenquan520/reading-analysis) |

B4 值得单独说一句：它和另外三种**质上不同**——它会**积累**。每用一次，内部的案例库和错题模式就厚一层。所以 B4 的价值随时间上升，值得长期挂着。

### C 类 · 产出加工

**它管什么。** 不生产新知识，只改变**材料的形态**：删 AI 味、归类、结构化、建索引。

**什么时候用。** 你已经有东西了，但它的形态不能直接交付或沉淀。

**这一类几乎无副作用，可以放心长挂。** 唯一的风险是「太顺手」——把不该改的东西也一起改了（比如过风格的时候顺手动了事实）。

**典型示例：**

- [humanizer-zh](https://github.com/op7418/Humanizer-zh) —— 改文字风格，保原意。
- obsidian-vault-governance（[来源未公开](#来源说明)）—— 改知识库的结构：归类、去重、建双链。

> **一个易混点**：obsidian-vault-governance 看起来像 D 类——它会移动、删除文件。但它主要干的是**材料形态的转换**，而且自带「只读盘点 → 列清单 → 确认后才执行」的强约束，把副作用收得很紧，所以归 C。判定看的是**主要作用**，不是「有没有副作用」。

### D 类 · 系统操作

**它管什么。** 直接读写外部系统：数据库、服务器、部署环境。

**什么时候用。** 真的要动线上或远端的东西时。

**这一类必须从严。** 三条硬规矩：

1. **只装你真在用的。** 一个不碰的数据库 skill 挂在身上，只是多一个被误触发的机会。
2. **必须配人工确认。** 不可逆操作（停机、删数据）动手前要复述影响并二次确认。
3. **先只读、后写入。** 变更前先跑查询确认现状，变更后再查一次确认生效。

**典型示例：**

- [byted-supabase](https://www.volcengine.com/) —— 操作火山引擎 Supabase，含高危的 workspace 暂停红线。
- nonebot-silent-failure-triage（[来源未公开](#来源说明)）—— 诊断运行中的服务。

## 搭配推荐方案

### 组合的基本逻辑

一次完整的作业，最多只需要四样东西，正好对应四层：

```
        ┌──────────────────────────────┐
        │  A 底座：怎么干               │  ← 长期固定，只留一个
        ├──────────────────────────────┤
        │  B 领域：干什么 + 怎么判对错   │  ← 跟当前主业走
        ├──────────────────────────────┤
        │  C 加工：产出成什么形态        │  ← 按需，可长挂
        ├──────────────────────────────┤
        │  D 执行：动什么（有副作用）    │  ← 从严，必须有人把关
        └──────────────────────────────┘
```

**不是每次都要四层。** 大部分任务只用得上 A 加 B。C 是「有产出之后」才加，D 是「要动真东西」才加。

### 四条搭配原则

1. **底座只留一个** —— 同层叠加会抢触发词、规则互斥。深浅两档二选一。
2. **领域层跟着主业走** —— 不相干的领域别挂着，它们会稀释匹配准确度。
3. **加工层可以长挂** —— 成本低、副作用小，只要盯住「别改到不该改的」。
4. **执行层从严** —— 装最少的、配确认的、先只读的。

### 四套现成搭配

**套餐 A · 应试闭环**（学习 → 做题 → 沉淀）

> 组成：**A**（一个底座）+ **B1 总管** + **B3 解题** + **B4 训练** + **C 知识治理**

- 逻辑：总管定「今天干什么」，分科解题和训练管「具体怎么打」，知识治理管「打过的别再忘」。
- 适用：有明确考试或学习主线的人。
- 注意：**只挂当前主战场的那一两科**，考完的科目及时撤下来。

**套餐 B · 内容生产**（素材 → 成稿 → 交付）

> 组成：**B**（领域产出初稿）+ **C**（风格加工）→ 交付

- 逻辑：领域 skill 负责「说得对」，加工 skill 负责「读着像人写的」。两步顺序不能反——先保正确，再改风格。
- 适用：要往外发东西的时候。
- 注意：加工层**只改风格不改事实**，改完自己再核一遍关键数字。

**套餐 C · 工程开发**（读上下文 → 改 → 验证 → 审核）

> 组成：**A**（开发向底座）+ **D**（需要的 MCP 能力，如搜索、浏览器、文档）

- 逻辑：底座给流程（先读记忆、最小改动、跑验证、多轮审核），D 层给「够到外部」的能力。
- 适用：碰真代码库时。
- 注意：MCP **能配就配、配不上就按降级规则走**，别为了凑齐工具卡住。

**套餐 D · 生产运维**（查现状 → 变更 → 验证）

> 组成：**D**（系统操作）+ **D**（诊断排障）

- 逻辑：一个负责「动」，一个负责「坏了怎么查」。两者都要强护栏。
- 适用：手上有真在跑的服务时。
- 注意：四套里唯一**默认该加人工确认**的一套。装之前先问自己：这东西误触发了，最坏会怎样？

## 附录 · 该不该装一个 skill

装之前过四个问题，任何一个答不上来就别装：

1. **它属于哪一层？** 判不出类别，说明你还没看懂它，先别装。
2. **这一层已经有 skill 了吗？** 有，且功能重叠 → 只留一个。
3. **我最近一个月会用到它吗？** 不会 → 等要用再装。装 skill 是零成本，但**误触发不是**。
4. **它有副作用吗？** 有 → 它属于 D 层，先确认它的护栏够不够。
